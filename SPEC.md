# VR Heaven — Telegram-бот партнёрской программы. Полное техническое описание

> Декларативное описание репозитория «от и до»: бизнес-модель, стек, структура,
> модель данных, интерфейсная модель, все сценарии, расписания, тесты и
> особенности реализации. Актуализировано после добавления мягкой отмены
> заказов и мульти-аккаунтов партнёров (60 тестов, все проходят).

## 1. Назначение и бизнес-модель

Бот автоматизирует учёт партнёрской программы компании VR Heaven. Модель следующая:

- **Партнёры** — офлайн-заведения (ПК-клубы и т. п.), которые раздают клиентам визитки с **промокодами**.
- Клиент называет промокод при заказе; **администратор** VR Heaven вручную вносит заказ в бота по факту оплаты.
- Партнёр получает **комиссию** от суммы каждого заказа со своим кодом. Ставка по умолчанию 10 %, задаётся индивидуально; в момент оформления заказа комиссия рассчитывается по текущей ставке партнёра и **фиксируется в заказе навсегда**:

$$commission = \mathrm{round}\left(amount \times \frac{percent}{100},\ 2\right)$$

- **Текущий (учётный) период** партнёра — множество всех его невыплаченных и неотменённых заказов (`payout_id IS NULL AND cancelled_at IS NULL`). Календарных границ у периода нет: **выплата закрывает период**, помечая все такие заказы выплаченными. Плановые дни выплат — 1-е и 15-е число месяца.
- Промокод одновременно является **логином** партнёра в личный кабинет внутри того же бота.

В системе две роли и, соответственно, два интерфейса в одном боте:

| Роль | Определение | Возможности |
|---|---|---|
| Администратор | Telegram ID входит в `ADMIN_IDS` из `.env` | Заказы, партнёры, сводка, выплаты, экспорт CSV; получает бэкапы и сводки по расписанию |
| Партнёр | Любой другой пользователь, авторизовавшийся по промокоду+паролю | Просмотр текущего периода и истории выплат; получает push-уведомления |

## 5. Модель данных (`db.py`)

СУБД — SQLite; включён `PRAGMA foreign_keys = ON`. Все временные метки хранятся строками **ISO 8601 в UTC** с точностью до секунды (`utcnow_iso()`), что даёт корректную сортировку как строк; при отображении конвертируются в часовой пояс из конфига. Денежные значения хранятся как `REAL` с округлением до 2 знаков (копеек) на всех точках записи.

### 5.1. Таблицы

**`partners`** — партнёры:

| Колонка | Тип | Описание |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | |
| `promo_code` | TEXT NOT NULL | Промокод = логин. **Не уникален глобально** (см. § 5.3) |
| `venue_name` | TEXT NOT NULL | Название заведения |
| `contact` | TEXT NOT NULL DEFAULT '' | Контакт представителя ('' = не указан) |

| `deleted_at` | TEXT NULL | Мягкое удаление; NULL = не удалён |

**`payouts`** — выплаты:

| Колонка | Тип | Описание |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | |

### 5.2. Миграции

`Database.init()` перед применением схемы вызывает `_migrate()` — цепочку идемпотентных шагов, каждый определяется по `PRAGMA table_info` и воспроизводит схему своей версии дословно (правки актуальной `SCHEMA` шаги не меняют). Свежая база пропускает все шаги и сразу получает актуальную схему:

- **v1 → v2**: снимает `UNIQUE` с `promo_code`, добавляет `partners.deleted_at` (пересоздание таблицы).
- **v2 → v3**: добавляет `orders.cancelled_at`; старый частичный индекс удаляется и пересоздаётся из `SCHEMA` с новым предикатом.
- **v3 → v4**: создаёт `partner_chats`, переносит туда привязки (`chat_id IS NOT NULL AND deleted_at IS NULL` — чаты удалённых партнёров не переносятся), пересоздаёт `partners` без колонки `chat_id`.

Миграции покрыты тестами с реальными базами v1, v2 и v3.

### 5.3. Ключевые инварианты данных

1. **Промокод закреплён только за «действующим» партнёром** (действующий = `is_active = 1 AND deleted_at IS NULL`). Проверка `promo_code_available(code, exclude_id)` считает код занятым только если он принадлежит действующему партнёру. Следствия: приостановка и удаление **высвобождают** код; повторная активация блокируется, если код тем временем выдан другому; вход по коду (`get_partner_by_code`) находит только действующего.
2. **Удаление партнёра — мягкое** (`delete_partner`): ставятся `deleted_at`, `is_active = 0`, все чаты партнёра отвязываются (`DELETE FROM partner_chats`). История заказов и выплат сохраняется и остаётся в экспорте; в списках, сводке и кабинете партнёр исчезает немедленно.
3. **Отмена заказа — мягкая** (`cancel_order`): условный `UPDATE ... SET cancelled_at ... WHERE cancelled_at IS NULL` (возвращает `False` при повторной отмене — защита от гонки двух админов). Отменённый заказ исключается из всех расчётов, но сохраняется в истории и экспорте; если он уже входил в проведённую выплату, запись выплаты не корректируется, а заказ остаётся привязанным к ней (админ предупреждается заранее).
4. **Один чат — один партнёр, у партнёра много чатов**: `chat_id` — PRIMARY KEY таблицы `partner_chats`; `bind_chat` — UPSERT, при конфликте чат переназначается новому партнёру, прочие чаты обоих партнёров не затрагиваются. Вход со второго устройства **не** выбивает первое.
5. **Выплата атомарна по смыслу**: `create_payout` берёт агрегат `unpaid_total` (COUNT/SUM по невыплаченным неотменённым), при нуле заказов возвращает `None`; иначе создаёт запись `payouts` и одним UPDATE (с фильтром `cancelled_at IS NULL`) привязывает к ней все заказы периода.

### 5.4. Полный перечень методов `Database`

- Партнёры: `create_partner`, `get_partner` (включая удалённых — для истории/экспорта), `get_partner_by_code` (только действующие), `promo_code_available`, `get_partner_by_chat` (JOIN через partner_chats; удалённые исключены), `list_partners(active_only)`, `set_partner_active`, `set_partner_password`, `set_partner_percent`, `delete_partner`, `bind_chat` (UPSERT), `chats_for_partner`, `unbind_partner_chats`.
- Заказы: `add_order`, `get_order` (JOIN с partners — код и название), `cancel_order` (мягкая отмена, условный UPDATE), `last_orders(limit=10)` (только неотменённые), `unpaid_orders`, `unpaid_total` (COUNT, Σamount, Σcommission), `unpaid_summary` (LEFT JOIN по всем неудалённым партнёрам — партнёры без заказов дают нулевые строки).
- Выплаты: `create_payout`, `payouts_for_partner(limit=30)`.
- Окно: `get_window`, `set_window` (UPSERT).
- Экспорт: `export_partners`, `export_orders`, `export_payouts` (включая удалённых партнёров, JOIN даёт промокод).

## 6. Оконная модель интерфейса (`window.py`)

Центральная UX-концепция: **в каждом чате всегда ровно одно сообщение бота** («окно»). Все экраны — редактирование этого сообщения; любой текст, отправленный пользователем (включая пароли), хендлеры удаляют из чата (`delete_user_message`, ошибки Telegram глотаются). ID окна хранится в таблице `windows`.

Два вида контента:

- **Обычные экраны** — текст в MarkdownV2 (parse mode по умолчанию у бота).
- **Табличные экраны** — нативные таблицы Telegram (**Bot API Rich Messages**, aiogram ≥ 3.29): бот передаёт классический HTML `<table>`; новые сообщения уходят методом `sendRichMessage` (`send_table` → `SendRichMessage` + `InputRichMessage(html=...)`), а обновление существующего окна — параметром `rich_message` метода `editMessageText` (отдельного `editRichMessage` в API нет). Дерево RichBlock вручную не собирается — Telegram строит таблицу из HTML-разметки.

Две точки отрисовки:

**`render(bot, db, chat_id, text, reply_markup, *, new_message=False, rich=False)`** — отрисовка по chat_id:
1. По умолчанию редактирует текущее окно. Ошибка `message is not modified` — no-op.
2. Любая другая `TelegramBadRequest` (окно потеряно/нередактируемо) → старое окно удаляется (ошибка удаления игнорируется), отправляется новое сообщение, его ID сохраняется как окно.
3. `new_message=True` — принудительно новое сообщение с удалением старого окна. Используется для **пуш-уведомлений**: редактирование не порождает notification у получателя, новое сообщение — порождает.

**`render_cb(bot, db, cb, text, reply_markup, *, rich=False)`** — отрисовка в ответ на нажатие inline-кнопки: **нажатое сообщение становится окном**; если текущее окно — другое сообщение (пользователь нажал кнопку на устаревшем экране), оно удаляется. Если нажатое сообщение нельзя отредактировать (например, это документ с кнопкой), оно удаляется и заменяется новым. Так инвариант «одного окна» самовосстанавливается при любом состоянии чата.

## 7. Утилиты (`utils.py`)

- **MarkdownV2**: `esc` (экранирование всех спецсимволов `` _*[]()~`>#+-=|{}.!\ ``), `esc_code`/`inline_code` (для `` `inline code` ``, используется для одноразового показа паролей «нажмите, чтобы скопировать»).
- **HTML (Rich Messages)**: `esc_html` (`html.escape` без кавычек), `table_html(headers, rows)` — сборка `<table><thead>…<tbody>…` с поячеечным экранированием.
- **Деньги**: `fmt_num` (`1234567.5 → "1 234 567,50"`, разделитель тысяч — пробел, десятичный — запятая, целые без дробной части), `fmt_money` (+ ` ₽`), `fmt_percent` (без хвостовых нулей: `10%`, `12,5%`).
- **`parse_amount(text) → float | None`** — единственный парсер числового ввода (суммы и проценты): терпит обычные и неразрывные пробелы, запятую как десятичный разделитель; округляет до копеек; допустимый диапазон **строго** $0 < v < 10^8$; всё прочее (включая `0`, отрицательные, `inf`, `nan`, мусор) → `None`.
- **Даты**: `utcnow_iso()` (хранение), `fmt_dt(iso, tz, fmt)` (отображение в TZ конфига, формат по умолчанию `%d.%m.%Y %H:%M`).
- **Пароли**: `gen_password(10)` — криптослучайный (`secrets`), алфавит без визуально неоднозначных символов (нет `0/O/o`, `1/l/I/i/L`); `hash_password` — **PBKDF2-HMAC-SHA256, 200 000 итераций, соль 16 байт на пароль**, формат `salt_hex$digest_hex`; `verify_password` — сравнение через `hmac.compare_digest` (защита от timing-атак), битые хэши → `False`.

## 8. Маршрутизация и протокол callback-данных

`main.py` подключает роутеры в значимом порядке: **сначала `admin.router`**, у которого и message-, и callback-фильтр `AdminFilter` (`from_user.id in config.admin_ids`), **затем `partner.router`** без фильтра — туда попадают все не-админы. Следствие: админ никогда не видит партнёрский интерфейс. `db` и `config` инжектируются в хендлеры через `Dispatcher["db"|"config"]`. Единственная команда бота — `/start` («Главное меню»).

Полный callback-протокол (`keyboards.py`):

| `callback_data` | Экран/действие |
|---|---|
| `am` | Меню админа |
| `cancel` | Универсальная отмена (сброс FSM → меню админа) |
| `ao:add` / `ao:p:{id}` / `ao:ok` | Новый заказ: старт / выбор партнёра / подтверждение |
| `ac:list` / `ac:o:{id}` / `ac:ok:{id}` | Отмена заказа: список / выбор / подтверждение |
| `ap:menu` / `ap:add` / `ap:list` / `ap:card:{id}` | Партнёры: меню / добавить / список / карточка |
| `ap:toggle:{id}` | Приостановить ↔ активировать |
| `ap:pwd:{id}` / `ap:pwdok:{id}` | Смена пароля: запрос / подтверждение |
| `ap:pct:{id}` | Изменить ставку (вход в FSM) |
| `ap:del:{id}` / `ap:delok:{id}` | Удаление: запрос / подтверждение |
| `sum` | Сводка текущего периода (rich-таблица) |
| `po:list` / `po:p:{id}` / `po:ok:{id}` | Выплата: список / подтверждение / проведение |
| `ex` | Экспорт трёх CSV |
| `plogin` / `pcancel` | Партнёр: начать вход / отменить вход |
| `pm` / `pp` / `ph` | Партнёр: меню / текущий период / история выплат |

FSM-группы: `AddOrderSG(amount, confirm)`, `AddPartnerSG(code, name, contact)`, `EditPercentSG(value)` — админ; `LoginSG(code, password)` — партнёр. Хранилище FSM — дефолтное (in-memory), т. е. незавершённые сценарии не переживают перезапуск — на этот случай есть fallback-хендлеры (§ 9.8, § 10.4).

## 9. Сценарии администратора (`handlers/admin.py`)

### 9.1. Добавить заказ (`ao:*`, `AddOrderSG`)
1. `ao:add`: список **только действующих** партнёров кнопками `код · заведение`; если действующих нет — сообщение с отсылкой в раздел «Партнёры».
2. Выбор партнёра → состояние `amount`, в FSM кладутся `partner_id`, `promo_code`.
3. Ввод суммы текстом (сообщение удаляется). Невалидная сумма (`parse_amount → None`) — повторный запрос без смены состояния. Валидная — комиссия считается по **текущей** ставке партнёра, состояние `confirm`, экран подтверждения: партнёр, сумма, «Комиссия N%: X ₽».
4. `ao:ok`: партнёр перепроверяется (мог быть удалён/приостановлен между шагами — тогда «заказ не оформлен»); создаётся заказ; партнёру с привязанным чатом уходит push «Новый заказ по вашему промокоду» (сумма, комиссия, накоплено к выплате, напоминание про 1-е/15-е). Экран результата сообщает, доставлено ли уведомление.

### 9.2. Отменить заказ (`ac:*`)
1. `ac:list`: последние **10 неотменённых** заказов кнопками `№id код · сумма · дд.мм` с пометкой «· выплачен» у закрытых.
2. Выбор → экран подтверждения (партнёр, сумма, дата) с предупреждением, если заказ уже включён в проведённую выплату. Выбор уже отменённого (устаревшая кнопка) — алерт «Заказ уже отменён».
3. `ac:ok:{id}`: мягкая отмена (`cancel_order`); при `False` (двойное нажатие или параллельная отмена вторым админом) — экран «Заказ уже был отменён» без повторного пуша. Во все чаты кабинета партнёра (если он не удалён) — push «Заказ отменён» с датой, суммой, новым накопленным остатком и отсылкой в поддержку `@VrHeaven`.

### 9.3. Добавить партнёра (`ap:add`, `AddPartnerSG`)
Три текстовых шага (каждый ввод удаляется из чата):
1. **Промокод**: приводится к нижнему регистру, валидация `^[a-z0-9_-]{2,32}$` (fullmatch); проверка занятости среди действующих.
2. **Название заведения**: непустая строка.
3. **Контакт**: произвольная строка; `-`, `—`, `–` трактуются как «без контакта» (пустая строка).

Перед созданием промокод **перепроверяется** (мог быть занят за время пошагового ввода — тогда «Подключение отменено»). Пароль генерируется автоматически, хэшируется, партнёр создаётся со ставкой 10 %. Экран результата: карточка партнёра + пароль в inline-code («нажмите, чтобы скопировать») с предупреждением, что он показывается **один раз** (в БД только хэш).

### 9.4. Карточка партнёра (`ap:card:{id}`)
Показывает: промокод, заведение, контакт (или «—»), ставку, статус (действующий/приостановлен), кабинет («подключён · устройств: N» / «не подключён»), «К выплате: X ₽ · заказов: N». Кнопки:

- **Приостановить/Активировать** (`ap:toggle`): приостановка освобождает код и закрывает новый вход в кабинет (уже привязанные чаты продолжают видеть кабинет и историю); активация блокируется алертом, если код за это время закреплён за другим действующим партнёром.
- **Новый пароль** (`ap:pwd` → подтверждение → `ap:pwdok`): старый хэш затирается, новый пароль показывается один раз; **все чаты кабинета отвязываются** — это штатный механизм отзыва доступа (устройства входят заново по новому паролю).
- **Изменить процент** (`ap:pct`, FSM `EditPercentSG`): принимается `parse_amount` со вторичным ограничением `≤ 100` (фактический диапазон — строго больше 0 и не больше 100, т. е. ставку 0 % ввести нельзя); действует только на новые заказы.
- **Удалить партнёра** (`ap:del` → подтверждение → `ap:delok`): экран подтверждения предупреждает о сумме невыплаченной комиссии, если она есть («после удаления сумма не будет выплачена»); удаление мягкое (§ 5.3, п. 2).

Во всех операциях по `{id}` партнёр перечитывается из БД, и удалённый/несуществующий даёт алерт «Партнёр не найден» — устаревшие кнопки безопасны.

### 9.5. Сводка (`sum`)
Rich-таблица `Код | Заказы | Оборот | К выплате` по строкам `unpaid_summary`, отфильтрованным правилом: показываются **действующие партнёры (даже с нулём заказов) и приостановленные с ненулевым остатком**; последняя строка «Итого», под таблицей «Итого к выплате: X ₽». Пустой список — «Партнёры пока не подключены».

### 9.6. Выплата (`po:*`)
1. `po:list`: партнёры с `orders_count > 0` (включая приостановленных) кнопками `код · сумма`.
2. `po:p:{id}`: подтверждение — заказы, оборот, **К выплате** жирным; повторная проверка «есть что платить».
3. `po:ok:{id}`: `create_payout` (гонка «уже нечего платить» обрабатывается отдельным экраном); во все чаты кабинета партнёра — push «Выплата проведена» (сумма, число заказов, «Открыт новый учётный период»). Экран админа: сумма, заказов закрыто, итог доставки уведомления.

### 9.7. Экспорт (`ex`)
Три CSV-документа отправляются в чат подряд, затем новое окно «Выгрузка сформирована». Формат: разделитель `;`, кодировка **UTF-8 с BOM** (`utf-8-sig`) — открывается в Excel без мастера импорта. Заголовки и человекочитаемые значения на русском; даты — в TZ конфига:

- `partners.csv`: id, промокод, заведение, контакт, комиссия_%, статус (`действующий`/`приостановлен`/`удалён`), устройств_кабинета (число подключённых чатов), создан — **включая удалённых**.
- `orders.csv`: id, промокод, сумма, комиссия, выплачен (`да`/`нет`), id_выплаты, отменён (дата отмены или пусто), дата — **включая отменённые**.
- `payouts.csv`: id, промокод, сумма, заказов, дата.

### 9.8. Fallback-хендлеры
- `@router.message()` (catch-all): любой текст вне сценария удаляется; если FSM пуст — окно возвращается в меню.
- `@router.callback_query()` (catch-all): нажатие кнопки устаревшего экрана (например, из FSM, потерянного при перезапуске) — сброс состояния, окно → меню, toast «Сессия обновлена».

## 10. Сценарии партнёра (`handlers/partner.py`)

### 10.1. `/start`
Если чат уже привязан к неудалённому партнёру — сразу меню кабинета (`код · заведение`, кнопки «Текущий период», «История выплат»). Иначе — приветственный экран с описанием программы и кнопкой «Войти».

### 10.2. Авторизация (`plogin`, `LoginSG`)
1. **Промокод** (= логин): приводится к нижнему регистру; ищется только среди действующих. Не найден — повторный запрос (число попыток на этом шаге не ограничено).
2. **Пароль**: до **5** неверных попыток (`MAX_LOGIN_ATTEMPTS`), после — сброс на приветственный экран («Попробуйте позднее или обратитесь в поддержку @VrHeaven»); вход надо начинать заново с промокода. Если партнёра деактивировали/удалили между шагами — экран «Доступ к кабинету закрыт» без раскрытия деталей.
3. Успех: `bind_chat` (UPSERT: если чат был привязан к другому партнёру — переносится только он; прочие устройства обоих партнёров не затрагиваются), меню с примечанием «Вход выполнен. Уведомления о заказах будут приходить в этот чат». К одному партнёру может быть подключено несколько чатов (совладельцы) — вход со второго устройства первое **не выбивает**; при входе с нового устройства ранее привязанные чаты получают push «Вход с нового устройства» (с отсылкой в поддержку — единственная сигнализация при общем пароле). Повторный вход при последующих визитах не требуется — сессия постоянная, «выхода» в интерфейсе нет (доступ отзывается сменой пароля или удалением партнёра).

Все вводы (включая пароль) немедленно удаляются из чата.

### 10.3. Кабинет
Каждый экран проходит через guard `_require_partner`: партнёр перечитывается по `chat_id`, и если привязка потеряна (партнёр удалён) — состояние сбрасывается, окно → «Доступ к кабинету закрыт» с кнопкой «Войти», toast «Доступ закрыт».

- **Текущий период** (`pp`) — rich-таблица невыплаченных заказов `Дата (дд.мм чч:мм) | Сумма | Комиссия`; показываются последние **25** (`MAX_TABLE_ROWS`) с примечанием «Показаны последние 25 из N»; итог: заказов, оборот, **К выплате**. Пусто — «Заказов в текущем периоде пока нет». Примечание: приостановленный партнёр с ранее привязанным чатом сохраняет доступ к этим экранам — блокируется только новый вход.
- **История выплат** (`ph`) — rich-таблица `Дата (дд.мм.гггг) | Сумма | Заказы` по последним **30** выплатам.

### 10.4. Fallback-хендлеры
Catch-all message: текст удаляется; вне FSM окно приводится к актуальному экрану (меню кабинета или приветствие); внутри FSM — не трогается (окно уже показывает текущий шаг). Catch-all callback: сброс состояния и приведение окна к актуальному экрану по факту привязки чата.

## 11. Push-уведомления партнёрам

Все пуши отправляются как `new_message=True` (иначе Telegram не показал бы notification), становятся новым окном каждого чата, уходят **во все чаты кабинета партнёра** (`_push_partner_chats`); сбой доставки в один чат не мешает остальным и не прерывает операцию — админ видит итог («Партнёр получил уведомление» при одном устройстве, «доставлено N из M устройств» при нескольких). Условие доставки: есть привязанные чаты (и партнёр не удалён).

| Событие | Содержимое |
|---|---|
| Новый заказ | Сумма заказа, комиссия партнёра, накоплено к выплате, «Выплаты проводятся 1-го и 15-го числа» |
| Отмена заказа | Дата и сумма исключённого заказа, новое накоплено к выплате, «Подробности — служба поддержки @VrHeaven» |
| Выплата проведена | Сумма, число заказов периода, «Открыт новый учётный период» |
| Закрытие периода (плановое, 1-е/15-е) | Отчёт «Учётный период закрыт» (таблица заказов) + «Выплата будет проведена в ближайшее время» |
| Вход с нового устройства | Предупреждение прежним чатам кабинета: «Если это не вы — обратитесь в поддержку @VrHeaven» |

## 12. Планировщик (`scheduler.py`)

`AsyncIOScheduler` в TZ из конфига, `misfire_grace_time = 3600` c (час на «догон» после простоя):

1. **`payout_day_job` — 1-го и 15-го в 10:00**: каждому админу — rich-сводка «День выплат · дд.мм.гггг» (тот же `admin_summary_text`); каждому партнёру с `orders_count > 0` и хотя бы одним привязанным чатом — отчёт закрытого периода (§ 11) **во все чаты кабинета** (ошибки по каждому чату изолированы). Сама выплата автоматически **не** проводится — только уведомления; проводит её админ вручную.
2. **`backup_job` — ежедневно в 03:00**: консистентная копия базы через `commit` + `VACUUM INTO` во временный файл; каждому админу отправляется документом `backup_ГГГГ-ММ-ДД.db`; сообщение с документом **становится окном** админа (прежнее окно удаляется, ID окна переводится на документ — поэтому у документа есть кнопка «В меню», а нажатие на неё корректно обрабатывается веткой «нередактируемое сообщение» в `render_cb`). Временный файл удаляется в `finally`. Восстановление: подложить файл бэкапа вместо рабочей базы.

Ошибки отправки каждому получателю изолированы (try/except с warning-логом).

## 13. Точка входа (`main.py`)

Последовательность: логирование (INFO) → `load_config()` → `Database.init()` (миграция + схема) → `Bot` с `DefaultBotProperties(parse_mode=MARKDOWN_V2)` → `Dispatcher` + инжекция `config`/`db` → роутеры (админ, затем партнёр) → старт планировщика → `set_my_commands([/start])` → `start_polling`. В `finally`: `scheduler.shutdown(wait=False)` и `db.close()`.

## 15. Безопасность

- Админ-доступ — строго по allowlist Telegram ID; фильтр стоит на роутере целиком (и message, и callback).
- Пароли: только хэши PBKDF2-HMAC-SHA256 (200k итераций, индивидуальная соль), сравнение constant-time; восстановление невозможно — только перегенерация; показ ровно один раз.
- Ввод пользователя (включая пароли) удаляется из чата; интерфейс не оставляет чувствительного следа, кроме одноразового экрана с паролем у админа.
- Брутфорс пароля ограничен 5 попытками на сессию входа; несуществующий промокод не раскрывает деталей; отключённый в процессе входа партнёр получает нейтральное «Доступ закрыт».
- Экранирование на обеих поверхностях вывода (MarkdownV2 и HTML rich-таблиц) — пользовательские строки (названия заведений и т. п.) не ломают разметку и не инжектируются.
- `.env` и файлы БД в `.gitignore`.

## 16. Особенности реализации, о которых стоит знать

1. **Деньги — `float`/`REAL`** с дисциплиной округления до 2 знаков на каждой записи. Для масштаба задачи (ручной ввод, суммы < 10⁸) приемлемо, но это осознанный компромисс, а не `Decimal`.
2. **FSM в памяти**: незавершённый пошаговый ввод теряется при перезапуске; catch-all-хендлеры штатно возвращают пользователя в актуальное меню («Сессия обновлена»).
3. **Отмена выплаченного заказа** не корректирует сумму уже проведённой выплаты — заказ лишь помечается отменённым, оставаясь привязанным к своей выплате (админ предупреждается). Возврат уже выплаченной комиссии — вне системы (осознанное решение: механизм денежных корректировок не строится).
4. **Ставка 0 %** фактически недоступна (парсер требует строго положительное число), хотя README формулирует диапазон как «от 0 до 100».
5. **`.env.example` отсутствует**, хотя README на него ссылается — единственное расхождение документации с репозиторием.
6. **Партнёр-админ невозможен как партнёр**: пользователь из `ADMIN_IDS` всегда попадает в админский роутер.
7. Уведомления — best-effort: сбой доставки не откатывает бизнес-операцию, но честно отражается в экране результата и в логах.
